# Collaboration method learned from this project

## English

### Scope discipline

Work only on **Space-Kitzler-Kontextschmiede** when the task is about this plugin. Do not broaden the task to unrelated plugins or projects. Keep the plugin's context distinct from the separate plugin-building workflow.

### Source discipline

- Start with the platform, project, file, and conversation the user named.
- Keep original sources, secondary handoffs, local copies, search results, and tool logs distinct.
- Report whether a source was listed, fetched, read, compared, or semantically checked.
- If a source is unavailable, identify exactly which source and what could not be verified.
- Do not turn an earlier assistant statement into proof that an original source was read.

### Delivery discipline

- When the user requests an artifact, produce the artifact itself rather than stopping at a proposed process.
- For an implementation request, make the authorized change, inspect the saved result, compare it with the target, and correct failures before reporting completion.
- Preserve existing skills and plugin behavior unless a specific change is justified.
- Do not change default prompts or raise the release version without a documented reason and verified acceptance.
- Finish the requested work with evidence, not with a claim of personal satisfaction or internal model emotion.

### Stepwise verification

A useful check asks: what did the tool actually return, what changed, and does that match the intended result? The check should be proportional to the change. Examples in this project include paginating the entire plugin file inventory, verifying skill paths rather than trusting a count, and calculating a checksum for the exact release archive.

### Communication style

Updates should be short and concrete: a verified finding, a change made, or an actual blocker. Avoid repeating plans when the user has asked for implementation. Preserve the user's corrections as design input, while labeling them as historical evidence rather than inventing a direct quote from a missing source.

### Current working agreement for future plugin tasks

1. Verify the existing plugin identity and live release before editing.
2. Follow the user's currently authorized scope.
3. Read the exact source files that own the requested change.
4. Make the smallest sufficient change that preserves the current product.
5. Verify both the stored artifact and the relevant real host behavior when available.
6. Record unresolved host or access limits plainly.

## Deutsch

### Scope einhalten

Wenn der Auftrag dieses Plugin betrifft, wird ausschließlich an der **Space-Kitzler-Kontextschmiede** gearbeitet. Die Aufgabe wird nicht auf andere Plugins oder Projekte ausgeweitet. Der Plugin-Kontext bleibt von der getrennten Pluginbau-Arbeit abgegrenzt.

### Quellen sauber halten

- Zuerst die Plattform, das Projekt, die Datei und die Unterhaltung verwenden, die der Nutzer benannt hat.
- Originalquellen, sekundäre Übergaben, lokale Kopien, Suchtreffer und Werkzeugprotokolle auseinanderhalten.
- Benennen, ob eine Quelle aufgelistet, abgerufen, gelesen, verglichen oder inhaltlich geprüft wurde.
- Wenn eine Quelle fehlt, genau angeben, welche Quelle nicht erreichbar war und was deshalb ungeprüft bleibt.
- Eine frühere Assistentenaussage nicht als Beleg dafür behandeln, dass eine Originalquelle gelesen wurde.

### Ergebnisse herstellen

- Wenn der Nutzer ein Artefakt verlangt, das Artefakt herstellen und nicht beim vorgeschlagenen Ablauf stehen bleiben.
- Bei Umsetzungsaufträgen die autorisierte Änderung ausführen, das gespeicherte Ergebnis erneut prüfen, mit dem Ziel vergleichen und Fehlschläge vor der Erfolgsmeldung korrigieren.
- Bestehende Skills und Pluginverhalten bewahren, solange eine konkrete Änderung nicht begründet ist.
- Standardprompts nicht ohne sachlichen Grund ändern und die Version nicht ohne dokumentierte Begründung und nachgewiesene Abnahme erhöhen.
- Die Arbeit mit Belegen abschließen, nicht mit Behauptungen über persönliche Zufriedenheit oder innere Modellgefühle.

### Schrittweise Prüfung

Eine brauchbare Prüfung fragt: Was hat das Werkzeug wirklich zurückgegeben, was wurde geändert und passt das zum beabsichtigten Ergebnis? Die Prüfung soll zur Änderung passen. Beispiele hier sind die vollständige Paginierung der Plugin-Dateiliste, die Prüfung konkreter Skillpfade statt einer bloßen Zählung und ein Prüfsummenvergleich für das exakte Releasearchiv.

### Kommunikationsstil

Statusmeldungen sollen kurz und konkret sein: ein verifizierter Fund, eine ausgeführte Änderung oder eine tatsächliche Blockade. Keine wiederholten Metapläne, wenn der Nutzer Umsetzung verlangt. Nutzerkorrekturen als Designhinweise bewahren und sie als historische Evidenz kennzeichnen, statt aus einer nicht erreichbaren Quelle ein direktes Zitat zu erfinden.

### Aktuelle Arbeitsvereinbarung für künftige Pluginaufträge

1. Vor einer Änderung Pluginidentität und Live-Release prüfen.
2. Den aktuell autorisierten Umfang des Nutzers einhalten.
3. Die Dateien lesen, die für die gewünschte Änderung maßgeblich sind.
4. Die kleinste ausreichende Änderung ausführen und das aktuelle Produkt bewahren.
5. Sowohl das gespeicherte Artefakt als auch das relevante echte Hostverhalten prüfen, sofern es zugänglich ist.
6. Offene Host- oder Zugriffslücken klar benennen.
